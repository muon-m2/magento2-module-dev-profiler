Magento 2 · developer mode only

Which copy of that template actually won?

A headless request profiler for Magento 2. It records theme-fallback resolutions, full-page-cache verdicts, layout opt-outs and SQL shapes for real storefront requests, then answers from the command line — no toolbar, no injected markup, nothing in the response body.

OSL-3.0 Magento 2.4.9 PHP 8.3 – 8.5 no database tables no cron

The questions it answers

Each one is normally answered by guessing, then by editing a file to see what changes.

Which file won the fallback?

Every resolution the request made — type, module, area, locale, theme — and the copies that lost. A theme override that silently never applied stops being invisible.

Why was this page not cached?

A hit, a miss, or uncacheable with the block that caused it named. Layout never runs on a cache hit, which is the fact the verdict rests on.

What issued 47 queries?

Statements folded by shape, so a loop appears once with ×47 and the file:line that produced it — not as 47 unrelated queries.

The verdict vocabulary

Four states, and the tool refuses to guess between them.

hit miss uncacheable n/a

n/a is not padding. A static asset has no layout and no page-cache verdict to give; reporting hit because layout never generated would be true of the mechanism and meaningless to the reader.

Install

Public repository, no authentication.

# composer.json: add the repository, then require it
composer config repositories.muon-dev-profiler vcs \
    https://github.com/muon-m2/magento2-module-dev-profiler
composer require --dev muon/module-dev-profiler

bin/magento module:enable Muon_DevProfiler
bin/magento setup:upgrade

It records nothing outside developer mode. The gate is compiled into the code path — there is no configuration field, no header and no query parameter that can switch it on, and it fails closed on an installation that cannot report its own mode.

Use

Load a page in the browser, then ask about it.

bin/magento muon:profile:show                    # the last full page request
bin/magento muon:profile:show 7f3a9c2e1b4d       # one specific run
bin/magento muon:profile:show --shadowed-only    # files that exist in more than one place
bin/magento muon:profile:show --sql              # statement shapes, findings first
bin/magento muon:profile:show --sql --nplus1=3   # stricter
bin/magento muon:profile:list                    # recent runs, newest first
bin/magento muon:profile:clear                   # empty the ring

Thresholds are applied when you read

Not when the page ran. The same capture can be re-examined at a different sensitivity without reloading anything, which matters when the interesting request is hard to reproduce.

What it records

One JSON document per request, in a 50-run ring under var/muon/profiler/
AreaRecorded
Requestmethod, URL, full action name, status, duration, peak memory, AJAX flag, page vs static
Contextstore code, store id, website id, resolved theme path
Layoutwhether layout generated, isCacheable(), handles, blocks declaring cacheable="false", constructor opt-outs with origin
Fallbackevery resolution: type, file, module, area, locale, theme, resolved path
Queriesstatement shape, execution count, timings, masked binds, calling file:line

What it does not record

Query results are never captured, and since 1.4.0 the statement text is stored as its normalised shape rather than verbatim — Magento inlines values into SQL at least as often as it binds them, so masking only the bound parameters would have left the rest in the clear. Bound values are masked by key and by shape; numeric ids are deliberately kept, because they are the evidence that separates an N+1 from a plain duplicate.

Muon_DevProfilerBoard

The same captures, rendered as a live web board: a polling ledger of recent runs, verdict banners, SQL and fallback panels, and a diff between any two runs. It reads through this module's analysis classes, so the board and the CLI can never disagree about the same token.
